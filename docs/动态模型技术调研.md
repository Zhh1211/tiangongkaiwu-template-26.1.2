# 动态模型（让方块真的动起来）技术调研

> 状态：**调研存档，尚未实施**。用户 2026-09-21 提出「以后可能把一些东西改成能动的模型」（学机械动力 / 或那个 g 开头的动画库）。
> 本文只做技术摸清与方案对比，不含任何代码改动。所有坐标均按项目铁律**直接读官方 maven-metadata.xml**，不靠搜索猜。
> 调研日期：2026-09-21。

---

## 0. 结论速览

| 路线 | 要不要方块实体 | 新依赖 | 工程量 | 适合什么 |
|---|---|---|---|---|
| **现状**：多模型变体 + `.mcmeta` 贴图动画 | 不要 | 无 | 已完成 | 只能"贴图层面"动（轮辐在贴图里走位），几何体不动 |
| **A. 原版手写旋转**（BE + `BlockEntityRenderer`，自己转 `PoseStack`） | **要** | **无** | 中 | **我们绝大多数装置**（轮盘转、碓头砸、龙骨板跑） |
| **B. GeckoLib**（骨骼动画库，即"g 开头的库"） | **必须** | GeckoLib（硬依赖） | 中高 | 复杂骨骼动作、多部件联动、整机变形 |
| **C. Flywheel**（机械动力用的渲染引擎） | 要（Visual 绑 BE，或 Effect 自管） | Flywheel | **很大** | 成百上千台装置同时动、GPU 实例化 |

**一句话建议**：我们想要的"轮子真的在转"**既不需要 GeckoLib 也不需要 Flywheel**——
路线 A 就能做到，且零依赖。真正要先想清楚的是：**愿不愿意为此引入"方块实体"**（我们至今所有装置都是零方块实体的）。

---

## 1. 硬约束（先记住这条，它决定一切）

> **Minecraft 的方块模型无法自定义渲染，没有方块实体就没有任何"逐帧"动画能力。**

- 原版方块渲染只认 blockstate → 模型 JSON 的静态对应关系，**模型 JSON 里没有"动画"这个概念**（1.21.1 无骨骼、无关键帧字段）。
- 官方 GeckoLib wiki 原话：*"Because blocks in Minecraft are static objects, it is not possible to outright animate a block without it also having a BlockEntity."*（方块是静态物，**除非它同时有方块实体，否则无法实现动画**，因为 GeckoLib 借的是 `BlockEntityRenderer` 体系。）
- 所以"让方块动"这件事，**唯一的技术入口就是 `BlockEntityRenderer`**。三条路线只是"谁来写这个 renderer"的区别。

---

## 2. 我们现在的"动"是什么（现状与天花板）

现状（B/C/D 批已落地）：

- 轮盘/碓头/龙骨板/风帆等，全部是 **`.mcmeta` 竖条动画贴图**（16×64 = 4 帧，游戏自动循环播放，零 tick 开销）+ **blockstate 变体切静态/动画两套模型**（`active=true/false`）。
- 也就是说：**"转"这个动作是贴在模型表面的一层画**，几何体本身一动不动。

天花板：

- 帧数越多文件越大，但**帧再多也改变不了"一张平面在播动画"**；侧面/厚度已通过建模补上，可"转"仍只是图案位移。
- 想用"每 tick 换一个 blockstate 变体"模拟旋转？**做不到平滑**：`scheduleTick` 最快 1 tick/次却也受限于方块更新，且变体数量会爆炸、网络同步巨大。**这条路已到顶。**

---

## 3. 路线 A：原版手写旋转（**推荐优先考虑**）

做法：

1. 给"要动的那一格"加方块实体（方块实现 `EntityBlock`，重写 `newBlockEntity`）。
2. 把模型拆成两组：**不动的部分**（支架）与**动的部分**（轮盘/碓头）。可以拆成两个模型 JSON 文件（`tong_che_static` / `tong_che_wheel`）。
3. 写 `BlockEntityRenderer`，在 render 里用 `PoseStack.translate/rotate` 把"动的那组"转到当前角度，再用模型渲染器画出来。
   - ⚠️ 1.21.1 的 renderer 签名与旧版不同，**要先用 `javap` 核实**再写（项目铁律）。
4. **角度不用联网同步**：服务端只需告诉客户端"在转/没转"（我们 blockstate 里已有 `active`，原版自动同步）；
   客户端用 `level.getGameTime() + partialTick` 自己算角度 → 每帧平滑、零网络开销。
   （Create 就是这么做的：转速存 BE 同步一次，角度由渲染层按时间推。）

优点：**零依赖**、完全可控、模型可继续用脚本生成、不引入外部授权/兼容问题。
缺点：没有骨骼系统，**每个动作都得手写插值**；复杂联动（连杆、多段骨骼）会很啰嗦。

---

## 4. 路线 B：GeckoLib（用户说的"g 开头的动画库"，基本可确定是它）

**坐标（已读官方 maven 核实）**

- 仓库：`https://dl.cloudsmith.io/public/geckolib3/geckolib/maven/`
- 坐标：`software.bernie.geckolib:geckolib-neoforge-1.21.1:4.9.3`（1.21.1 分支最新 **4.9.3**，共 26 个版本）
- 许可 MIT；CurseForge 项目 id 388172。

**它是什么**：基于 Blockbench「Bedrock 模型 + 动画」的骨骼动画库，支持实体/方块/物品/盔甲。
能力包括动画控制器（状态机）、**服务端触发动画**（`triggerAnim`）、停播触发动画、无状态动画系统（4.7+）、发光贴图、UV 旋转等。

**做"会动的方块"的完整步骤**（官方 wiki）：

1. 方块实现 `EntityBlock`（或其子类），`newBlockEntity` 返回你的 BE；
2. 方块重写 `getRenderShape` → `RenderShape.ENTITYBLOCK_ANIMATED`（**关掉原版模型渲染**，否则会和自定义渲染打架）；
3. BE 实现 `GeoBlockEntity`，`registerControllers` 里注册动画控制器；
4. 建一个继承 `GeoBlockRenderer` 的渲染器并注册；
5. 模型与动画用 **Blockbench 导出**（bedrock geometry `.geo.json` + animation `.animation.json`）。

**代价（对我们而言）**

- **必须引入硬依赖**：BE 要实现 `GeoBlockEntity`，这不是"可选集成"能绕开的——
  即玩家必须装 GeckoLib 才能玩（与现在 JEI/Jade 的"装了才有提示"模式不同）。
- 模型工作流转向 Blockbench：现在的**纯 Python 手写 JSON 模型管线要部分放弃**（或并存：静态方块继续脚本，动的方块走 Blockbench）。
- 渲染本质仍是 **BE renderer（CPU 提交顶点）**，不是 GPU 实例化；装置数量大时不如 Flywheel。
- 4.9.x 与网上大多数教程（4.7 时代）**API 有差异**，要用 `javap` 对着真实 jar 核实后再写。

**适合它的场景**：水碓的连杆往复、多段骨骼联动、整机"折叠/展开"这类**真骨骼动画**。只为"轮子转"而引入它，性价比低。

## 5. 路线 C：Flywheel（机械动力的渲染引擎）

**坐标（已读官方 maven 核实）**

- 仓库：`https://maven.createmod.net/`（官方 README 的 NeoForge + MDG 写法）
- 坐标：`dev.engine-room.flywheel:flywheel-neoforge-api-1.21.1:1.0.7-48`（compileOnly）
  + `dev.engine-room.flywheel:flywheel-neoforge-1.21.1:1.0.7-48`（runtimeOnly）
- 1.21.1 分支最新 **1.0.7-48**；MIT；基岩是 GPU 实例化渲染。

**它是什么**（不是"动画库"，是渲染引擎）：把实体/方块实体渲染改走 GPU 实例化路径，允许自定义顶点格式与 shader。核心概念：

| 概念 | 含义 |
|---|---|
| **Visual** | 相当于原版 renderer，但按需更新、可并行 |
| **Instance** | 一次可渲染对象（上传到 GPU）；**不更新就沿用上次状态**，这是它省 CPU 的关键 |
| **Plan** | 把线程池暴露给 Visual 的手段（帧/刻级更新） |
| **Render Origin** | 渲染原点（不是相机位置），原点移动时所有 Visual 重建 |
| **Effect** | 一种"自由游戏对象"，**不需要方块实体**即可使用渲染系统（但生命周期与同步要自己管） |

**Create 的 `ROTATING` 实例**（值得学的点）：实例数据里存 `rotationalSpeed`（度/秒）、`rotationOffset`、`rotationAxis`，
**转速交给 shader 按时间算角度** → 旋转中的机器**每帧不需要重新上传实例数据**，CPU→GPU 带宽几乎为零。
这就是 Create 能让一大堆齿轮同时转还不卡的原因。

**代价**：要写 Visual/Instance、自定义 instance 类型、可能还要写 GLSL；官方 README 明确说 shader 系统"WIP、会有破坏性变更"。
对我们的需求（几种装置、几十台）来说**工程量是数量级上的过度设计**。

## 6. Create 是怎么做的（可借鉴的四点）

1. **动力状态存方块实体**：`KineticBlockEntity` 存 `speed`（转速）/`capacity`（应力容量）/`stress`，网络标识 `network`；
   发电装置继承 `GeneratingKineticBlockEntity`，只需实现 `getGeneratedSpeed()`（水车按四周水流算 `flowScore`）。
2. **双路渲染**：有 Flywheel 就走 Visual（GPU），没有就退回原版 BE renderer 自己转矩阵——
   **说明"CPU 手写旋转"是完全可行的保底方案**（正是我们的路线 A）。
3. **角度由渲染层按时间推**，不必每帧同步（见上）。
4. **水车是 3×3 一次成型**：玩家挖好 3×3 坑、右键中心即自动铺满整个轮子（与我们筒车"放一格自动展开 3×3"的思路一致，
   这一块我们**已经做对了**）。

> ⚠️ 关于 Create 水车"3×3 里只有一个方块实体"的源码细节，本次**未逐行核实**（仅从玩家侧行为与文档确认形态），

## 7. 对我们的建议（分阶段）

**阶段 0（现在）**：保持 `.mcmeta` 动画。装置能玩、性能零负担，**不必急**。

**阶段 1（推荐，等用户点头）**：挑 1 台装置做**路线 A 试点**——最合适的是**筒车**（它本来就 3×3、中心格天然适合挂 BE）：
- 只给**中心那一格**加 BE（BE 数量 = 装置台数，不是格数）；
- 模型拆成「支架（静态）」+「轮盘（活动）」，BER 里转轮盘；
- 角度按 `gameTime + partialTick` 算，`active` 沿用现有 blockstate，**不加网络同步**。
- 试点成功再推广到碓头（往复）、龙骨板（循环）、风帆（旋转）。

**阶段 2（看需要）**：若真要"整机骨骼动画"（连杆、折叠），再引入 **GeckoLib**（届时用 `javap` 对 4.9.3 核实 API）。

**阶段 3（暂不需要）**：Flywheel——除非以后要做"大片机械集群"。

### 若走路线 A，要注意的坑

- **多点方块 + BE 的配合**：3×3 自动展开时只能主格带 BE；挖**非主格**要正确清掉主格的 BE（我们现在的收回逻辑已有，要接上）。
- **存档兼容**：老档里已放下的装置没有 BE，加载后需要能自愈（或提示重建）——这点要在实施前想好。
- **`ENTITYBLOCK_ANIMATED`**：若走 GeckoLib 必须设；走路线 A 则用普通 BE renderer + 原版模型照旧（静态部分仍由 blockstate 渲染）。
- **性能**：BE renderer 是 CPU 渲染，装置几十台无压力；批量上百台才需要考虑 Flywheel。
- **用户机器（X240 / HD4400 / 4GB）**：任何新渲染路径都要先在实机跑一遍再推广，别一次改一批。
