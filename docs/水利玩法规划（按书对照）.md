## 2. P0——「至少要做」清单（书里明说，现在缺失或假的）

### P0-1 提水上坡（书：挽水入筒，倾于梘内）
**缺口**：筒车只灌水平邻格；梘不认上方。河边车永远灌不了坡上田。
**推荐方案（甲）**：**提水只由机器完成**——
- 筒车/龙骨车（运转中）把水送给**车体周围含上方 2 格**内的梘或田（机器是主动方，只出水不进水，天然无成环问题）；
- 梘保持现状（平送 + 向下），不做竖直接力——提升高度 = 轮高（3×3 轮 ≈ 提 3 格），这正好贴合书里"筒的行程就是轮的半径"。
- 不推荐给梘加"认上方"：两条梘上下叠会互相供水成环，要额外防环逻辑，复杂且不像书。
**验收**：河边低处立筒车 → 用梘沿 2 格高的坡把水引上高田 → Jade 看到田水上涨；拆车断水。

### P0-2 效率刻度落地（书：五亩／倍之／二亩）
**缺口**：三种车灌田一样快。
**方案**：把**动力值直接当"提水流量"**：筒车 12 / 牛车 10 / 踏车 5 / 拔车 2 / 辘轳 2 / 桔槔 1。
- 梘与车直灌的补水间隔 = `48 / 流量` tick（≈ 筒车 4s、牛车 4.8s、踏车 9.6s、拔车 24s 补 1 格田水）；
  踏车:牛车 = 1:2，正对书里"牛则倍之"；筒车最快且不需人值守，正对"昼夜不息"。
- 梘从**上游装置**读流量（WaterDevices 已有 emittedPower，一处改动）；没有上游（纯挨着水源）的梘保持现状或不供水——**待拍板**。
- Jade 同步显示「流量 N」（它已显示动力，同一数值）。
**验收**：同一片田分别接四种车，掐表测补水速率 ≈ 2 : 5 : 10 : 12。

### P0-3 堰陂障流要真花工夫（书：堰陂障流，激轮使转）
**缺口**：挖一格河岸就有"非水源的水"，筒车白得激流。
**方案**：驱动水判定从"车下任一格是流水"提高到——**轮盘下沿（水中那 3 格）至少 2 格是流动水**（非水源）。
效果：静水塘放车不转；把河道收窄/垒坝逼出连续激流才转；填回堰停转。原版水机制天然支持，无需新方块。
**验收**：静水塘不转；垒堰后转；拆堰停转（提示文案同步改）。

### P0-4 观感：让装置真的动（已拍板路线 A，此处排期）
**缺口**：轮子/龙骨板/碓头是平面板动画——"像不像"的最大单项。
**方案**：按 `docs/动态模型技术调研.md` 路线 A：**只给筒车中心格加 BE + BER**，模型拆「支架/轮盘」两组，按 `gameTime + partialTick` 旋转；验证一台后再推广碓头（往复）与龙骨板（循环）。
**验收**：绕轮走一圈，轮辐真的转；没水/栓木时静止；装置几十台不卡。

### P0-5 排涝→栽种闭环（书：去澤水以便栽種）
**缺口**：风帆车抽干后留下坑+普通地形。
**方案**：抽掉水源时，把该格**转换为新田**——水下方是泥土系/沙时，直接变 `rice_stalk` 可种植的干田底土（或掉落泥土+一格"垦地"标记，待拍板细节）；这样"救潦造田"是真实收益。
**验收**：雨天把一片浅沼抽干，抽干处能直接下种/建田。

## 9. 动力系统要不要学 Create 的「转速/应力」+ 大模型方向（2026-09-27 用户提出，仅评估）

> 用户原话：动力系统学一下机械动力（有没有必要引入转速与应力这两个单位）；多搞点大模型
> （风车没必要一小格，很奇怪）；多搞点模块化/可自定义结构（想多大多大）。
> **本节只评估，未定案。**

### 9.1 「转速」——建议不引入

- 书里**没有「快慢」概念，只有「效率」**（灌田亩数、碓的能力）——单一「动力值」（12/10/5/2）已表达全部信息。
- 转速的表现力不需要独立单位：**动画转速直接由动力值驱动**（动力高 → 轮转得快），玩家看得见动力差异即可。
- 引入转速 = 玩家多学一个数、代码多一套换算，且无书源支撑。Create 造 RPM 是为齿轮箱/变速箱那套机械传动真实性服务，我们没有那批方块。

### 9.2 「应力」——建议引入（书页里叫「劲」，不搬 Create 的名字）

- **它修复现有动力网的一个真实漏洞**：碓只检查「轴上 power ≥ min_power」，所以**一台踏车（5）理论上能同时带任意多台碓**——动力没有总量分配，「并具图」那种一台水车配一套碓的量感是假的。
- 机制草图：网络可分配动力 = Σ动力源 − 距离衰减 − 已占用消耗（碓 3/台，将来的磨/砻各定额）；后到的机器分不到就不转，或全网降速（Create 式，二选一待定）。
- **与书的完美咬合**：动力分不到 → 碓「不及」→ **出糙米**（书：「不及則粗」）。动力不足的惩罚不是坏档，是降质——书里的机制直接变成动力分配玩法的反馈，不用发明任何书外惩罚。
- 书页话术：「一台车的劲就那么些，带多了各家都舂不透」。

**风帆车 1 格确实怪**（书「揚郡以風帆**數扇**」是数面帆的大装置）——升级为大结构。分层走：

## 10. Create 源码研读笔记（一）：应力网络与水车流量（2026-09-27，仓库 G:/workspace/_refs/Create，分支 mc1.21.1/dev）

> 用户已 clone（MIT，可搬）。本节为第一轮研读结论：动力分配（§9.2）与筒车取水（§2 段4/段5）的落地方案。

### 10.1 应力网络（kinetics/KineticNetwork.java，全文仅 181 行——比预想简单得多）

**数据结构**：网络对象按 `Long id` 归组（BE 里存 network id + 上游 source pos）；
持有 `sources`（动力源 → 容量）与 `members`（全体成员 → 消耗）两张表，以及 `capacity/stress` 两个总和。

**算法就两个求和**：
- `capacity = Σ 源容量`（`calculateCapacity`）
- `stress = Σ 成员消耗`（`calculateStress`）
- 每个成员的定额来自**数据表**（`BlockStressValues.getImpact(block)`）——碓 3、磨 X，就是注册一行的事
- 数值都乘 `|speed|` 调制（转速越高产能与消耗同比放大）——我们不引入转速，乘数恒 1 即可，算法完全兼容
- **过载判定**：`capacity < stress` → 整个网络 `overStressed` → 速度归零（Create 式全停）
- **脏重建**：任何变化只标 `networkDirty`，该成员下次 tick 重算并 `sync()` 全网；网络在方块增删时由 RotationPropagator 重新分 id
- **卸载记账**：已卸载区块的成员用 `unloadedCapacity/unloadedStress/unloadedMembers` 三个数记账，不持有对象

**对我们（§9.2 「劲」）的落地结论**：这个结构可整体照搬（MIT），改动比预想小一个量级。
碓的「不及则粗」＝网络过载时的产物侧降级，正好接在 overStressed 状态上。

### 10.2 水车流量（waterwheel/WaterWheelBlockEntity.determineAndApplyFlowScore）

- 低频结算（`lazyTick`），不逐帧；
- **用原版流体的真实流向向量打分**：遍历轮周边检查格，取 `fluid.getFlow(level,pos)`，投影到轮面切向（rotate 90°），|dot| > 0.5 记 ±1 分——**正反转、水流强弱全部真实**，还能区分 lava；
- 分数变了才重算速度并传播（`setFlowScoreAndUpdate`）。

**对我们（筒车）的落地结论**：现在「车下有非水源的水即转」可以升级为同样的 flowScore 打分——
**「堰陂障流」的工程感就能落地**（静水 0 分不转；垒堰逼出正向流，分数越高劲越大），且天然支持水轮正反转（书里没说转向，但观感真实）。

### 10.3 一个设计抉择（新增，待拍板）：距离衰减 vs 总量分配

Create 的网络**没有距离衰减**（全网处处等价），距离成本靠轴线建材体现；我们现状是 `-1/格` 衰减、无总量。
若两者都留会双重惩罚。**推荐：统一成一个系统**——取消 `-1/格`，改为「轴每格也算 0.2 消耗」：
- 距离长 = 网损大 = 可带机器少（距离成本保住）；
- Σ消耗 ≤ Σ动力源（总量分配保住）；
- 一个规则管两件事，且与 Create 同构（研读成本低）。

## 8. 流体化方向（2026-09-27 用户提出，规划中——若拍板则替代 §2 中 P0-1 / P0-2 的实现方式）

**用户提议**：水利整成真正的流体系统（学机械动力的架构，做精点、后面卷能用上）；筒车/龙骨车只作动力源；在梘（用户称"水槽"）上加一个小机器为流体提供动力（＝泵）。

### 8.1 我的看法：赞成，四条理由

1. **不是从零造轮子**：NeoForge 有标准流体设施（`FluidStack` / `IFluidHandler` / capability 暴露 / 流体注册），接上去就行——动手前按项目铁律用 `javap` 核实确切签名。
2. **复用是真实的**：《作咸》卤水、《膏液》榨油、《五金》熔融浇铸（书里的合金）全是流体场景。第一版把平台立住，后面三卷直接接。
3. **架构干净**：**动力网（已有）× 流体网（新）两个正交系统，机器在交点**——正是机械动力验证过的模式（它家熔炉/搅拌/铸造也都是流体+动力交点）。
4. **书里本来就支持"动力与功能分离"**：《粹精》「激水转轮头，**一节转磨成面，二节运碓成米，三节引水灌稻田**」——宋应星自己就是"一个动力源带多个功能机"的思维。所以"车只是动力源"不是偏离书，而是"一举三用"的模块化表述。

### 8.2 三件套命名（每一件都有书源）

| 方块 | 角色 | 书源 |
|---|---|---|
| 车（筒车/牛车/踏车/拔车） | **动力源**：出动力给轴，不再直接灌田 | 水利节四车 |
| **筒**（新方块，＝用户说的"小机器"/泵） | **提水机**：吃动力（邻轴或贴车），从相邻的水源/流水/含水梘抽水，注入相邻**任意方向**（含上方）的梘或容器 | 筒车的"筒"——「**挽水入筒**」；通用化＝"以机代人力"的提水件（同传动轴的先例：书外通用件，书页交代定位） |
| 梘 | **流体槽**：逐段储水、重力自流（高处段向低处段流动） | 「一一傾於**梘內**，流入畝中」 |
| 出水（梘侧向补水） | 用水端：梘侧向有田即按流量补水 | 「流入畝中」 |

**龙骨车的圆场**（要写进书页）：书里龙骨车体内本有龙骨提水（「其內用龍骨拴串板，關水逆流而上」），游戏里把"提水"拆成通用件**筒**、车只出动力——正是"一节运碓"式的分节思路，也与"并具图"的各器分工相合。

### 8.3 关键设计决策（我的推荐）

1. **流动模型：逐段重力流（推荐）**——每段梘存水量（方块实体 int），每 10 tick 结算：本段比下游段多 ≥1 且下游未满 → 移 1 单位；泵向相邻段注入。有"水往低处流"的直观感、实现直白、几十段规模无性能压力。
   （备选：Create 式连通器网络均衡——更物理，但要网络合并管理，第一版不建议。）
2. **水经济学简化**：取水＝无限源（筒邻水源/流水即可抽）；灌田＝消耗；**不模拟全局水量守恒**。
3. **流体＝原版水**：第一版不注册任何新流体；但梘/筒**必须暴露标准流体 capability**——这是"后面能用上"的技术核心，卤水/油/熔液以后直接走同一网络。
4. **方块实体转向**：梘/筒带 BE（存水量）——旧档的抽象梘需自愈迁移；BE 到位后 P0-4 的 BER 动画（轮旋转 + 梘水位渲染）顺手做。
5. **风帆车保持独立**：排水**不入**流体网（书：「去水非取水也，不適濟旱」——排掉的水不能白得）。
6. **性能纪律**：逐段低频结算（10 tick 一次），无逐帧模拟；几十台规模进实机测过再定。

### 8.4 成本直说

- 工作量 ≈ 非流体版 P0 的 **1.5–2 倍**（BE + 流体能力 + 梘水位渲染 + 筒 + 旧档迁移）。
- 换来：三卷复用的流体平台 + 正确架构 + 动画地基。**值得，但要一次做对、控制范围**。
- **第一版范围红线**：只做「水 + 梘网 + 筒 + 出水 + 标准 capability」；新流体注册/桶装交互/高级管道等，等对应卷（作咸/膏液/五金）再上。
